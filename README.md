# My-portfolio-App
# 1. サービス概要
- **このサービスはどんなサービスか：**
  ランニング・筋トレ・勉強など、分野ごとに異なる単位（km・時間・回数など）を自由に設定し、自発的な努力の「累積量」と「目標までの差分」を横断的に一元管理できるサービスです。
- **誰の、どんな課題を、どう解決するか：**
  すでに自発的に継続できている社会人を対象に、複数ジャンルの努力成果を統合して数字で可視化することで、「精神論に留まっていた自信をデータで立証する」環境を提供し、適切なペース配分と自分全体のトータルマネジメントおよび総合的な成長実感をサポートします。

---

# 2. このアイデアはどこから生まれたか

## 2-1. きっかけとなった体験・感情
趣味や自己研鑽としてランニング、筋トレ、資格勉強などを日常的に続けている中で、「自分は今日までに累計で何km走り、何時間勉強し、何回筋トレを行ってきたか」振り返りたくなったことがきっかけです。

日々の努力は習慣化しており苦ではない場合でも、これまでの「累積の努力量」と「目標までの現在地」をまとめて可視化する手段がなく、自分がどれだけの積み上げをしてきたのかを感覚でしか把握できないことにモヤモヤとした違和感を覚えました。

## 2-2. なぜそれが「気になった」のか
私自身、目標に向かって努力を積み重ねた結果を定量的なデータを見ることで自信に繋げる性格だからです。

「継続すること（日数）」そのものよりも、「自分がどれだけの量を積み上げてきたか」という客観的な数値データで、自分自身の成長を実感し、自信の根拠になると考えているためです。

---

# 3. 課題の整理（表面的になっていないか）

## 3-1. 表に見えている困りごと
複数の活動（ランニング・筋トレ・勉強など）における「今までの努力量」と「目標までの進捗（あと何日・あとどれくらいか）」が、数字で同時に可視化できない。

## 3-2. 本当に解決したい課題は何か
- **なぜ困るのか？** → 努力の累積データと、目標までの適切なペース配分（残り日数と必要量）が分からないから。
- **なぜそれが問題なのか？** → 定量的なデータがないため適切なペース管理ができず直前の帳尻合わせになったり、自分の頑張りの成果が数字として残らず実感が湧きにくいため。
- **なぜ実感が湧かないと問題なのか？** → 努力に対する自信が「精神論メイン」になってしまい、自分の成長を数字で証明できないから。

→ **本当に解決したい課題：**
すでに継続して何かを行っている人が、自分の積み上げた成果（累積値）と目標までの距離を数字で客観的に証明できず、自信が精神論に留まってしまうことや、適切なペース配分ができないこと。

# 4. 想定ユーザーについて

## 4-1. 想定しているユーザー
「習慣化」の段階はすでにクリアしており、趣味や自己研鑽（資格勉強・トレーニング等）を自発的に日常に組み込んでいる20〜30代の社会人。
- **年齢設定（20代後半〜30代前半）：** 明確な目的意識を持って自主的に勉強や運動を継続する習慣が身についている年代。
- **生活・状況設定：** 平日の仕事終わりや休日に、勉強・筋トレ・ランニングなどを複数こなしており、異なる単位（時間・km・回数・ページ数など）の活動を統合して管理したいニーズがある。
- **環境設定：** 既存の「習慣化アプリ」では個別の数値追跡にとどまりトータルな成長感が得られず、「特化型アプリ」では複数ジャンルを横断した総合的な管理ができないハードルを感じている。

## 4-2. 自分とユーザーの距離
**「自分自身（および過去の自分）」**

自分自身が「継続はできているが、積み上げた数字で把握したい」という課題に直面していた当事者であるため。

## 4-3. 実際に使われる可能性について
- **最初のアクション：** 既に何らかの記録（スプレッドシートやメモ）をつけている知人や自分自身。
- **代わりに使っているもの：** 
  - スプレッドシート（事務的で自作・管理が面倒）
  - 習慣化アプリ（個別の回数や日数追跡に留まり、複数項目の統合や総合的な管理ができない）
  - 特化型アプリ（分野ごとに分散する）
- **置き換えてまで使う理由：** 単位を自由に設定でき、複数ジャンルの「累計積み上げ量」と「目標との差分」を一箇所で直感的に可視化・立証し、総合的なトータルマネジメントができるから。

## 4-4. ユーザーがサービスを導入して利用するまでのイメージ
- **きっかけ：** 「最近頑張っているけど、結局累計でどれくらいやったんだろう？」と自分の積み上げ量を振り返りたくなった瞬間。
- **最初の一歩：** 目標と独自の単位（km、時間、回など）を登録し、今日の数値を入力する。
- **継続する理由：** 記録するたびにグラフや総数が更新され、「自分の努力の積み上げ」が視覚的な実績・自信として蓄積されていく快感を得られるから。

# 5. 既存サービス・競合調査

## 5-1. 似たサービスの調査
- **サービス名：** 
  - **Habitify などの習慣化アプリ**
    - *できること：* 日数や回数の記録など、日々の習慣を継続させるための機能に優れている。
    - *限界・不満点：* Habitifyなど一部アプリには日数以外に回数を追えるものもあるが、あくまで個別項目の管理がメインであり、複数項目どうしを統合して「自分の総合的な活動量」を評価することはできない。
  - **Nike Run Club / Studyplus などの特化型記録アプリ**
    - *できること：* ランニングの距離や勉強時間など、特定の単一ジャンルに特化した詳細なデータが取れる。
    - *限界・不満点：* ジャンルごとにアプリが分散してしまい、同時進行で取り組んでいる複数の活動を横断して管理・比較ができない。

## 5-2. それでも自分が作りたい理由
既存の習慣化アプリや特化型アプリを調査した結果、これらは「個別の習慣の継続」や「単一ジャンルの記録」には長けているものの、「複数の努力が互いにどう影響し合っているか（総合的な活動量）」を把握できないという物足りなさを感じました。

自分が本当に作りたいのは、複数の努力を1箇所にまとめ、以下の体験を生み出せるツールです。
1. **自分という1人の人間としての総合的な成長実感**
   個々の把握（例：勉強なら「学力アップ」など単一の能力向上）にとどまらず、勉強＋運動など複数の努力をトータルした「総量」を可視化することで、自分そのものへの自信につなげる。
2. **努力どうしの相互関係（相乗効果・コンディション）の把握**
   「なぜ今月は運動はできたのに、勉強はできなくなっているんだろう？」といった状態の波を、当時の記録やメモ（例：仕事のミスが続いており運動はストレス発散になったが、勉強は仕事を想起させるため避けていた等）と照らし合わせ、自分が最も努力できる環境やコンディションの法則性に気づけるようにする。

## 5-3. 差別化を「体験価値」で表現する
- **私のアプリの差別化ポイント：**
  「継続の有無（日数）や回数」だけでではなく、それらを踏まえた「積み上げた総量（数値）」にフォーカスする。また、複数ジャンルの努力を1箇所でまとめて「自分の総合値」として可視化できる点。

# 7. このアプリで実現すること
- **MVPで作る機能：**
  - ユーザー認証機能（Deviseによるログイン / 新規登録）
  - 目標（タイトル、目標値、期限日）の登録・管理機能
  - カテゴリ・単位（km、時間、回数など）の登録機能
  - 実績の記録機能（日付、数値、単位、メモ）

- **本リリースで作る機能：**
  - グラフ表示機能
    - 日別累積値
    - 週間実績
    - 月間実績
    - 目標達成率
  - リマインド通知機能

# 8. このアプリの懸念点とその対策

## 懸念点①：複数単位の計算ロジックの複雑化
- **何が問題になりそうか：** 単位が自由（km、時間、回数など）なため、データベース設計や集計クエリ（SQL）の設計が複雑になり、予期せぬ計算ミスやパフォーマンス低下が起きる可能性がある。
- **対策：** 記録データ（Records）とカテゴリー（Categories）の主従関係を明確にし、集計処理はRailsモデル側でメソッドとして適切に切り分けてテストコードを書きながら実装する。

## 懸念点②：レスポンシブ対応とグラフ等のUIデザインの迷い
- **何が問題になりそうか：** スマホやPCなど多様な画面サイズで数値やグラフが崩れやすく、デザインにこだわりすぎて開発が停滞するリスクがある。
- **対策：** MVPの段階ではTailwind CSSを活用して工数を削減し、「日々の入力のしやすさ」を最優先のUI設計にする。

# 10. 技術スタック（手段としての技術）

## 10-1. 使用予定の技術
- **言語 / フレームワーク：** Ruby（3.2.3）, Ruby on Rails（7.1.6）, JavaScript
- **DB：** PostgreSQL（15）
- **認証：** Devise
- **インフラ / 環境：** Docker / Docker compose, Render
- **スタイリング / グラフ：** Tailwind CSS / Chartkick / Groupdate

## 10-2. 技術選定の比較検討
| 候補 | 採用/不採用 | 理由 |
| :--- | :--- | :--- |
| **Ruby on Rails** | 採用 | MVCの仕組みが体系化されており、素早く堅牢なWebアプリを構築できるため。 |
| **PostgreSQL** | 採用 | 本番環境を想定した堅牢なRDBの扱いや、複雑な集計クエリの学習を兼ねるため。 |
| **Devise** | 採用 | ユーザー登録、ログイン、パスワード再設定、メール確認など、Webアプリに必要な豊富な認証機能が標準で揃っており、セキュアな機能を実装できるため。 |
| **Docker / Compose** | 採用 | 開発環境の差異をなくし、本番を見据えた再現性の高いインフラ構築を学ぶため。 |
| **Tailwind CSS** | 採用 | 素早く柔軟にオリジナルデザインを構築でき、クラス名の命名に悩む工数を削減できるため。 |
| **Bootstrap** | 不採用 | あらかじめ用意されたコンポーネントで手軽に構築できる反面、デザインのカスタマイズ性が低いため。 |
| **Chartkick + Groupdate** | 採用 | RailsのActive Recordと連携し、SQLの複雑な日付集計処理（Groupdate）からグラフ描画（Chartkick）までを最小限のコードで安全かつ高速に実装できるため。 |
| **Chart.js（単体利用）** | 不採用 | 高度なカスタマイズが可能な反面、Railsからのデータ受け渡しやJavaScript側の描画ロジック記述量が増え、開発スピードが低下するため。 |

## 10-3. キャッチアップ不足の懸念
- Deviseの機能拡張・カスタマイズ： 標準機能は強固で豊富である一方、独自のビューの変更、ルーティングの調整、メール通知の設定などでつまずかないよう、主要なカスタマイズ手順を事前に検証します。
- Chartkick + Groupdateによる集計・日付の範囲指定やタイムゾーンの扱いなど細かな挙動について理解を深め、MVP開発を通じて段階的に実装・調整を進めていきます。
